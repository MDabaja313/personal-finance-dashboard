@AGENTS.md

**Current phase:** Phase 7 (Mutations) in progress — CP1 (write foundation), CP2 (accounts + categories) and CP3 (ordinary transactions) are complete; CP4 (movements) has not started. See `DEVELOPMENT_PLAN.md` for the authoritative phase roadmap. **The owner can now create, edit, and archive/unarchive accounts and categories, and create/edit/delete ordinary income, expense and refund transactions. Nothing else is writable.** `authenticated` holds column-scoped `INSERT`/`UPDATE` on exactly `accounts`, `categories` and `transactions` (`supabase/migrations/20260827120001_account_category_writes.sql`, `20260828120002_transaction_writes.sql`) plus **`DELETE` on `transactions` only**; movements, budgets, bills, bill_occurrences, goals, goal_contributions, net_worth_snapshots, and profiles remain read-only. Writes go through `lib/actions/**` (Server Actions: validate → `attempt()` the mutation → redirect on `unauthenticated`, else return a safe `ActionState` → precise `revalidatePath` calls, never `revalidatePath("/")`) into `lib/data/mutations/**` (the only layer issuing PostgREST writes; fenced away from `next/navigation` and `next/cache` by ESLint, and never taking an owner id from its caller — `getOwnerId()` re-verifies on every write). `lib/validation/**` (Zod) narrows untrusted form input first; the database is still the final authority, via the column-scoped grants, the operation-specific RLS policies, and three guard triggers: `accounts_guard_update()` (type immutable; opening balance editable only with zero transactions; archiving requires a derived balance of exactly zero, unarchiving unconditional), `guard_category_kind_change()` (kind immutable once referenced by any transaction, budget, or bill — rename and archive stay allowed), and `assert_transaction_refs()` (`BEFORE INSERT OR UPDATE` on `transactions`: no row dated later than the owner's **own** calendar day, computed from `profiles.timezone` and never from server UTC; no archived account; a category must be active and kind-compatible — income needs an income category, expense/refund an expense one; adjustments carry no category — and it covers movement legs too, so CP4 inherits it). `transaction_kind` gained `adjustment` (`20260828120001_transaction_kind_adjustment.sql`, enum-only by necessity), which is **readable, filterable and badged but not writable**: the entry form offers income/expense/refund only, `transactions_update_own_ordinary` refuses both to target an adjustment and to produce one, and reconciliation is CP5. `transactions_delete_own_non_movement` and `transactions_update_own_ordinary` both carry `movement_id IS NULL`, so transfer/card-payment legs stay visible in history but are unreachable from the ordinary surface. **Transaction creation is idempotent by client-generated UUID**: the create form mints one key per mounted form and posts it as the row's `id`, so a retry collides on the primary key; `createTransaction` re-reads its own row on `23505` and compares the *complete* normalized payload — exact match is a successful retry, same key with a different payload is a `conflict`, and a key belonging to another owner falls through as an ordinary unique conflict. No idempotency table, no middleware. `Category` carries `isArchived`; `getCategories()` still returns archived rows, so historical labels keep resolving, while the entry pickers offer active accounts/categories only, narrowed to the kinds the selected transaction kind permits. Account management lives on `/accounts`, category management in a section of `/settings`, transaction entry/editing on `/transactions` (a sheet, plus per-row Edit and two-step Delete on ordinary rows only); forms are plain `<form>` + `useActionState`, with no form library. `npm run test:mutations` is the integration harness — it rebuilds the local database, signs in as the real owner, and drives the real Server Actions, mutation DAL, and production read DAL, mocking only `lib/data/supabase.ts` plus `next/cache`/`next/navigation` (notably **not** `getToday()`, so the posted-date ceiling under test is the real one). All ten production `lib/data/**` read functions (`getAccounts`, `getCategories`, `getTransactions`, `getRecentTransactions`, `getBudgets`, `getBills`, `getUpcomingBills`, `getGoals`, `getNetWorthHistory`, `getToday`) are Supabase-backed. `lib/data/supabase.ts` is the one DAL seam allowed to import `lib/supabase/**`; every read calls `getOwnerId()` (verified via `getClaims()`, never `getSession()`) before issuing its query, independent of route-layer render order. `getAccounts()`/`getGoals()` read the `account_balances`/`goal_balances` `security_invoker` views; `getBills()` is a two-query projection (active `bills`, then their `scheduled` `bill_occurrences`, reduced to one occurrence per bill in TypeScript — PostgREST can't truncate per-parent-row); `getTransactions()` orders `date DESC, created_at DESC, id ASC` and is read through a bounded, cumulative "Load more" reveal window (`app/(app)/transactions/page.tsx`, `lib/data/filters.ts`) — never an unbounded full-history fetch; `getNetWorthHistory()` queries `ORDER BY month DESC LIMIT n` and reverses in TypeScript for chronological display; `getToday()` derives the calendar date from `profiles.timezone` via the real clock (`lib/data/clock.ts`), with no dev-only `MOCK_TODAY` branch — seeded data ages naturally against the real date. `public.movements` remains unreadable by `authenticated` (no grant, no policy) — no Phase 6 read needed it. `lib/mock/dal.ts` is retained only as the `npm run test:parity` oracle; no production code imports it. `Transaction.kind` may now be `adjustment`, and `lib/finance/transactions.ts` counts it as neither spending nor income — like a movement leg, it moves a balance without being an economic event. `merchant` search is a plain `ILIKE` scan with no `pg_trgm` index — recorded as a future performance optimization, not a Phase 6 correctness blocker, since it's provably correct against the single-owner dataset. `lib/supabase/**` (browser/server/proxy Supabase clients), `lib/auth/**` (the app-facing identity facade and `signIn`/`signOut` Server Actions), `proxy.ts` (session-cookie refresh via `getClaims()`), `app/(auth)/login`, and the `requireUser()` guard in `app/(app)/layout.tsx` are implemented and verified both statically (`lib/auth/posture.test.ts`) and at runtime (`npm run auth:verify`, `scripts/verify-auth.ts`). No signup route exists, or ever will. Locally, `npm run auth:reset-local` rebuilds the database around one real, login-capable owner at the same deterministic UUID the fixture seed targets — plain `npm run db:reset` alone is not login-capable; rerun `auth:reset-local` after it if you need to sign in. The Supabase schema, RLS/grants, triggers, views, seed data, and the hardened snapshot-writer (Phase 4) are implemented and verified both locally and hosted (`supabase/migrations/**`, `supabase/tests/database/**`) — unchanged since Phase 4 apart from the additive Phase 7 CP2/CP3 migrations above — no Phase 4 migration file has ever been edited (CP3 does drop and re-create `transactions_sign_by_kind_ck` with a wider predicate, in its own forward migration, preserving every existing branch verbatim). `error.tsx`/`loading.tsx`/`not-found.tsx` boundaries exist, `lib/errors.ts` defines the typed DAL error taxonomy, `TransactionFilters` supports `from`/`to`, and `lib/data/**` has explicit ordering contracts. ## Commands

- `npm run dev` — start the dev server (http://localhost:3000)
- `npm run build` — production build
- `npm run start` — run the production build
- `npm run lint` — run ESLint
- `npm run typecheck` — `tsc --noEmit`
- `npm test` — run Vitest once, fully offline (fixtures + mocked `lib/data/supabase.ts`); `npm run test:watch` for watch mode. Scoped to `lib/**/*.test.ts` (`lib/finance/**` and fixture coherence, `lib/auth/**` unit + static posture tests, `lib/data/**` unit tests) — no component tests.
- `npm run test:parity` — the Phase 6 parity suite (`tests/parity/**`) proving each Supabase-backed `lib/data/**` function agrees with the `lib/mock/dal.ts` fixture oracle. Requires local Supabase running and `npm run auth:reset-local` already applied — not offline like `npm test`. It reads only, so run it **before** `test:mutations`: the mutation suite leaves rows the oracle knows nothing about.
- `npm run test:mutations` — the Phase 7 CP2/CP3 mutation suite (`tests/mutations/**`). Real writes, as a real authenticated owner, against local Supabase: real Server Actions → real validation → real `lib/data/mutations/**` → read back through the production read DAL. Only `lib/data/supabase.ts`, `next/cache`, and `next/navigation` are mocked — `getToday()` is deliberately real, so the owner-timezone posted-date ceiling is exercised rather than stubbed. **Its global setup rebuilds the local database** (it runs `scripts/provision-owner.ts`) and refuses to start unless `NEXT_PUBLIC_SUPABASE_URL` is a loopback address — it can never touch hosted. Runs serially. Rerun `auth:reset-local` afterward to clear the rows it created.
- `npm run auth:reset-local` — rebuild the local database around one real, login-capable owner (`scripts/provision-owner.ts`). Plain `npm run db:reset` alone is not login-capable.
- `npm run auth:verify` — runtime-verify the auth flow against a running `npm run dev` (`scripts/verify-auth.ts`).
- `npm run db:test` — run the pgTAP database test suite (`supabase test db`). It runs against the local database **as it currently stands**: it neither re-applies migrations nor re-seeds (verified directly — a hand-edited row survives the run and fails `010-seed-parity.sql`). So run `npm run db:reset` (or `auth:reset-local`) first whenever migrations changed or the data has drifted, or the suite will report on a stale schema.

## Architecture invariants

- **Money is integer cents**, branded `Cents` (`lib/types`). Never floats, never `parseFloat`. Convert to decimal only in `lib/format/currency.ts`. A `bigint` crossing the DB→TS boundary must pass a `Number.isSafeInteger` check — never silently coerced.
- **Percentages are display-only, divide-first**: `percentage(num, den)` in `lib/finance/money.ts` computes `(num/den)*10000` rounded, never `(num*10000)/den` — the latter can silently exceed the safe-integer range before dividing. Returns `null` for a zero denominator or non-finite result; render as `—`, never `NaN`/`Infinity`. A meter's *text* percentage may exceed 100 (over-budget, over-funded goal) — only its CSS width is clamped to [0, 100].
- **Dates are `'YYYY-MM-DD'` strings.** Never `new Date('YYYY-MM-DD')` on a financial date. Parse via `lib/finance/dates.ts` (`parseCalendarDate`, re-exported from `lib/format/date.ts`); day-count math (`daysBetween`) uses `Date.UTC`, not local-midnight subtraction, so it's DST-safe.
- **Transaction meaning is `kind` + sign together, never sign alone.** `income` +, `expense` −, `refund` +, `transfer`/`credit_card_payment` source − / destination +, `adjustment` either sign. The two movement kinds are paired legs sharing one `movementId` (exactly two, summing to zero), excluded from income/spending/cash-flow but still visible in each account's own history; `adjustment` is likewise excluded (it reconciles a balance rather than recording an economic event) and carries no category. **Entry forms collect a non-negative magnitude and the server derives the sign from the kind** (`signedAmountFor` in `lib/types/enums.ts`, mirroring `transactions_sign_by_kind_ck`) — a signed field would let a well-formed submission contradict its own kind. Zero is legal for ordinary rows and stays exactly `0`, never `-0`. See `lib/types/index.ts` and `lib/finance/transactions.ts`.
- **Account balances are signed** (assets +, liabilities −). Display splits it: `totalAssets`/`totalLiabilities` (positive magnitude) and `netWorth` (signed sum), such that `netWorth === totalAssets - totalLiabilities`. `NetWorthSnapshot` commits to the same convention explicitly (`netWorthCents` stored, not implied) — never compare it against raw signed balances.
- **`today` is always an explicit parameter**, supplied by `lib/data/clock.ts` (`getToday()`, fixed at `MOCK_TODAY` during the mock phase). `lib/finance/**` never reads the clock — ESLint blocks `Date.now()`/`new Date()` there.
- **Every list-returning `lib/data/**` function has an explicit `ORDER BY`-equivalent sort** — see `docs/database-schema.md §17` for the full contract per function. Never rely on fixture array order. When a DAL function only guarantees a *technical* order (e.g. `getBudgets()`'s `category_id ASC`, since it has no join to `categories`), the calling page applies its own semantic display order using data it already fetched — a UUID must never become a visible sort order. `getTransactions()` orders `date DESC, created_at DESC, id ASC`; `created_at` never appears on the `Transaction` DTO.
- **Layer boundaries** (enforced by `eslint.config.mjs` where the layer exists):
  - `lib/data/**` — the only layer that queries the database (or reads mock fixtures now). `'server-only'`, returns DTOs.
  - `lib/mock/**` — fixtures. Only `lib/data/**` may import them; `app/**` and `components/**` are blocked.
  - `lib/supabase/**` — the only layer that reads Supabase env vars / constructs clients. Reachable only from `lib/auth/**` and the root `proxy.ts`; `app/**` and `components/**` are blocked from importing it directly.
  - `lib/auth/**` — the app-facing identity seam: `getVerifiedClaims()`/`requireUser()` (`lib/auth/session.ts`) and the `signIn`/`signOut` Server Actions (`lib/auth/actions.ts`). `app/**` and `components/**` call into this, never into `lib/supabase/**` directly. No `signUp` — public signup is disabled, permanently.
  - `lib/finance/**` — pure calculations: no `lib/data`, `lib/mock`, `lib/supabase`, React, or clock access.
  - `components/**` — UI + local state/interactivity only. No DB/DAL/fixture access, no `process.env`, no derived financial arithmetic (call the tested `lib/finance` function instead), no `lib/supabase/**` or `lib/auth/**` value imports (the action/session helpers arrive as props; a type-only `lib/auth/types` import is fine, since it carries no runtime access).
- **Auth:** use verified claims/user identity (`getClaims()` for page/proxy protection, `getUser()` when an up-to-date Auth record is specifically needed) for server-side authorization — never `getSession()`, since cookie-backed session data isn't itself verified. See `docs/auth-design.md`. RLS is enabled on every table even though this is single-user — the publishable key is public. `service_role` never runs in application code. This posture (no `getSession()` authorization, no `signUp()`, the import boundaries above) is a static regression test, not just documented convention — see `lib/auth/posture.test.ts`.
- **Server Actions are independently reachable endpoints** — re-verify auth and row ownership inside the DAL, not just at the page level.
