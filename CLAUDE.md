@AGENTS.md

**Current phase:** Phase 7 (Mutations) — CP1 (write foundation), CP2 (accounts + categories), CP3 (ordinary transactions), CP4 (transfers + credit-card payments), CP5 (reconciliation + current-month snapshots, the **REAL-FINANCE GATE**), CP6 (budgets + goals + goal contributions) and CP7 (bills + bill occurrences) are all complete; **CP8 has not started.** See `DEVELOPMENT_PLAN.md` for the authoritative phase roadmap. **CP7 completed the finance domains: the owner can create, edit and archive/unarchive accounts, categories, goals and recurring bills; create/edit/delete ordinary income, expense and refund transactions; create/edit/delete transfers and credit-card payments; reconcile any active account's balance (creating — and removing — an auditable `adjustment`); manage current-month budgets; append goal contributions; and mark any bill occurrence paid, skipped, or back to scheduled.** `authenticated` holds column-scoped `INSERT` on `accounts`, `categories`, `transactions`, `movements`, `budgets`, `goals`, `goal_contributions` and `bills`; `UPDATE` on all of those except `movements` and `goal_contributions`, plus a three-column `UPDATE (status, transaction_id, paid_on)` on `bill_occurrences`; and `DELETE` on `transactions`, `movements` and `budgets` only (`supabase/migrations/20260827120001_account_category_writes.sql`, `20260828120002_transaction_writes.sql`, `20260828120003_movement_writes.sql`, `20260830120001_budget_goal_writes.sql`, `20260831120001_bill_writes.sql`). **`net_worth_snapshots` and `profiles` are the only tables that remain read-only, and both stay that way.** **CP5 changed no table grant at all** — reconciliation is a new operation over CP3's existing privileges, delivered as two functions (`supabase/migrations/20260829120001_reconciliation.sql`, `20260829120002_current_snapshot.sql`).

**Reconciliation (CP5) never rewrites history.** The owner states what an account's balance actually is; `public.reconcile_account(p_account_id, p_as_of, p_desired_balance_cents)` — `SECURITY INVOKER`, `search_path = ''`, no owner parameter — derives `delta = desired − (opening_balance_cents + SUM(transactions.amount_cents))` **in SQL** and inserts one row: `kind = 'adjustment'`, the fixed literal merchant `'Balance adjustment'`, `category_id`/`movement_id` explicitly null, `date = p_as_of`, `amount_cents = delta` (either sign — `transactions_sign_by_kind_ck`'s adjustment branch is unconstrained). A zero delta writes **no row** and reports success, which is also what makes reconciliation **idempotent with no idempotency key**, unlike CP3's and CP4's creates: a resubmission computes its delta against the balance the first submission already corrected. Computing the delta in the database rather than the client is correctness, not tidiness — a client-computed difference would be wrong whenever a transaction landed between the balance read and the post. `opening_balance_cents` is deliberately **not** the reconciliation mechanism (editing it restates every balance the account ever reported, which is why `accounts_guard_update()` freezes it once the account has any transaction). The posted-date ceiling and the archived-account refusal are left to `assert_transaction_refs()` rather than restated. **Liability input is a magnitude normalized above the database:** credit/loan accounts ask "Amount currently owed" and take a non-negative figure, which `lib/data/mutations/reconciliation.ts` negates into the internal balance **from the account's stored type**, never from anything the client sent; asset accounts take a signed actual balance (an overdrawn account is a real state). The RPC's parameter keeps exactly one meaning — the desired internal signed balance — so an overpaid card (a legitimately positive `credit` balance) stays expressible. **An `adjustment` is permanently uneditable and always removable by its owner:** `transactions_update_own_ordinary` carries `kind <> 'adjustment'` in both `USING` and `WITH CHECK`, while `transactions_delete_own_non_movement` never excluded adjustments — so the correction path is remove-and-reconcile-again, and `deleteAdjustment` is a reconciliation-specific mutation that refuses anything that is not an owned, non-movement adjustment (it adds no privilege). An adjustment moves the balance and net worth and appears in **no** economic total: `countsAsSpending`/`countsAsIncome` are allowlists, so it is excluded **by kind**, not by sign and not by lacking a category.

**`public.refresh_current_net_worth_snapshot()` is the only `SECURITY DEFINER` function in this application, and the only thing that writes `net_worth_snapshots` on the owner's behalf.** Everything else CP2–CP5 added is `SECURITY INVOKER`; this one cannot be, because `private.write_net_worth_snapshot` is owned by `finance_snapshot_writer`, `authenticated` has no `USAGE` on `private`, and `net_worth_snapshots` has no write grant for `authenticated` and never will. It is narrow by construction: **zero parameters** (so no owner and no month can be addressed — `pronargs = 0` is asserted), owned by the existing `NOLOGIN`/`NOSUPERUSER`/`NOBYPASSRLS` writer rather than by `postgres`, `search_path = ''`, `EXECUTE` revoked from `PUBLIC`/`anon` and granted to `authenticated` alone, and carrying exactly one new privilege — column-scoped `SELECT (id, timezone)` on `profiles` behind `profiles_select_writer`, narrowed to the calling request's own row. The `CREATE ON SCHEMA public` that `ALTER FUNCTION … OWNER TO` requires is granted for that one statement and revoked immediately. **The month comes from the owner's `profiles.timezone`, never server UTC** — the same expression `assert_transaction_refs()` and `getToday()` use. The bridge reads the JWT `sub` through `private.request_owner_id()` rather than `auth.uid()`, because inside a definer body the current role is `finance_snapshot_writer`, which has no `USAGE` on schema `auth` — and that grant cannot be made from a migration at all (schema `auth` belongs to `supabase_auth_admin`); `160-current-snapshot.sql` asserts the two agree so the duplication cannot drift. **There is no historical rebuild surface:** `private.write_net_worth_snapshots_for_range` keeps its Phase 4 posture with no wrapper of any kind, and CP5 accepts the historical limitations that follow (no `opened_on`, no archived-at reconstruction, no prior-month rebuild, no repair of an old snapshot after a backdated edit) — live derived balances are authoritative, the snapshot series is a secondary trend. **The refresh is always a secondary failure.** It is a separate PostgREST request and therefore a separate transaction, so `lib/data/mutations/snapshots.ts` awaits it **after** the primary write commits and swallows a failure, logging only a sanitized operation noun plus an `AppErrorCode` — never an amount, a balance, a merchant, a row, an owner id, or a raw driver payload. Refreshed after: account create, an opening-balance edit, archive/unarchive (the writer's inclusion rule is `is_archived = false`), ordinary transaction create/update/delete, movement create/replace/delete, reconciliation, and adjustment removal. **Not** refreshed after: any category write, a metadata-only account edit, a deduplicated create, a no-op movement replace, or a zero-delta reconciliation. **Known inherited limitation — two reachable states, not one.** Phase 4's writer carries *two* sign guards (`v_assets_cents < 0` and `v_liabilities_cents < 0`) and raises `data_exception` (SQLSTATE 22000) **before writing anything** rather than storing either magnitude negative. Both are now reachable through ordinary supported writes: **aggregate assets below zero** (every non-`credit`/`loan` account summed — an account opened at a negative balance, a CP3 expense overdrawing one, a transfer out, or a CP5 reconciliation to a negative observed balance, which the asset form invites outright; the aggregate goes negative whenever the owner's whole asset position does, e.g. one overdrawn current account and no savings), and **aggregate liabilities above zero internally** (a CP4 card payment overpaying a card, or CP5 zeroing the other debts that were offsetting one). In both cases the primary write **commits**, the action reports success, exactly one sanitized line is logged (`[invalid_input]`, since 22000 is class 22 — no figures, no raise text), and the existing snapshot row is left **byte for byte unchanged** — stale, never wrong — until the next balance-affecting write that returns the aggregate to a valid sign, which recomputes the whole month. CP5 does not alter the Phase 4 writer; both guards are characterized in `160-current-snapshot.sql` and at the action layer in `tests/mutations/snapshots.test.ts`.

**Movements (CP4) are written only through two `SECURITY INVOKER` RPCs, and that is structural rather than stylistic.** A movement is a parent plus exactly two legs; a childless movement fails `validate_movement()` at `COMMIT`, and a leg naming a movement that does not exist yet fails the **non-deferrable** composite FK immediately — so, since PostgREST issues one statement per request in its own transaction, no sequence of PostgREST calls can produce a movement at all. `public.create_movement` and `public.replace_movement` take **no owner parameter** (it comes from `auth.uid()`), use `search_path = ''`, and were the first two of the eight functions `authenticated` may `EXECUTE` anywhere in this schema (CP5 added `reconcile_account` and `refresh_current_net_worth_snapshot`; CP7 added `create_bill`, `replace_bill`, `set_bill_archived` and `maintain_bill_schedule`). Editing is delete-and-recreate under the movement's *original* id inside one transaction, so a refused replacement leg leaves the original pair byte-for-byte intact; deleting is one statement on the parent, whose cascade takes both legs. `movements` has **no `UPDATE` grant and no `UPDATE` policy, permanently** — its row is `(id, user_id, kind)`, and retyping `kind` in place would contradict every leg's own kind. Both leg signs, both merchant labels ("Transfer to X" / "Payment from Y", composed in SQL from the movement's kind and the other account's name) and the null category are **derived server-side**; the form posts a positive magnitude and two account *roles*, never a sign and never free text. A credit-card payment's destination must be a `credit` account (the convention `lib/types/index.ts` states); nothing constrains the source's type. Movement creation is idempotent by three client-minted UUIDs (movement + both legs) compared against the complete normalized persisted payload, exactly as CP3's is; `replaceMovement` short-circuits an edit that changes nothing, because a needless rewrite would give both legs a new `created_at` and reorder same-day history. `lib/data/movements.ts` (`getMovements(ids)`, `Movement` DTO) reads a pair **by movement id**, not by pairing two rendered rows, so an edit works when the partner leg falls outside `/transactions`'s reveal window. Movement writes revalidate `/transactions`, `/dashboard`, `/accounts`, `/analytics` — **never `/budgets`**, since `countsAsSpending` is an allowlist of `expense`/`refund` and a leg is excluded by kind. CP4 writes no net-worth snapshot; CP5 owns snapshots. Writes go through `lib/actions/**` (Server Actions: validate → `attempt()` the mutation → redirect on `unauthenticated`, else return a safe `ActionState` → precise `revalidatePath` calls, never `revalidatePath("/")`) into `lib/data/mutations/**` (the only layer issuing PostgREST writes; fenced away from `next/navigation` and `next/cache` by ESLint, and never taking an owner id from its caller — `getOwnerId()` re-verifies on every write). `lib/validation/**` (Zod) narrows untrusted form input first; the database is still the final authority, via the column-scoped grants, the operation-specific RLS policies, and three guard triggers: `accounts_guard_update()` (type immutable; opening balance editable only with zero transactions; archiving requires a derived balance of exactly zero, unarchiving unconditional), `guard_category_kind_change()` (kind immutable once referenced by any transaction, budget, or bill — rename and archive stay allowed), and `assert_transaction_refs()` (`BEFORE INSERT OR UPDATE` on `transactions`: no row dated later than the owner's **own** calendar day, computed from `profiles.timezone` and never from server UTC; no archived account; a category must be active and kind-compatible — income needs an income category, expense/refund an expense one; adjustments carry no category — and it covers movement legs too, so CP4 inherits it). `transaction_kind` gained `adjustment` (`20260828120001_transaction_kind_adjustment.sql`, enum-only by necessity); it is **readable, filterable, badged, and writable only through CP5's reconciliation**: the ordinary entry form offers income/expense/refund only, and `transactions_update_own_ordinary` still refuses both to target an adjustment and to produce one. `transactions_delete_own_non_movement` and `transactions_update_own_ordinary` both carry `movement_id IS NULL`, so transfer/card-payment legs stay visible in history but are unreachable from the ordinary surface — and the reverse holds too: no movement action takes a leg id, and `lib/data/mutations/movements.ts` never issues a statement against `transactions`. **Transaction creation is idempotent by client-generated UUID**: the create form mints one key per mounted form and posts it as the row's `id`, so a retry collides on the primary key; `createTransaction` re-reads its own row on `23505` and compares the *complete* normalized payload — exact match is a successful retry, same key with a different payload is a `conflict`, and a key belonging to another owner falls through as an ordinary unique conflict. No idempotency table, no middleware. `Category` carries `isArchived`; `getCategories()` still returns archived rows, so historical labels keep resolving, while the entry pickers offer active accounts/categories only, narrowed to the kinds the selected transaction kind permits. Account management and balance reconciliation live on `/accounts` (Edit and "Reconcile balance" are mutually exclusive disclosures — one restates history, the other appends a dated correction), category management in a section of `/settings`, transaction entry/editing on `/transactions` (a sheet, plus per-row Edit and two-step Delete on ordinary rows only), and movement entry/editing in a **separate** "Move money" sheet on the same page — whose Edit/Delete render on exactly one leg, the source (negative) one, chosen on the server so a pair never grows two sets of controls and the destination leg gets none rather than disabled ones. An `adjustment` row gets a two-step **Remove** control (whose confirmation says it changes the account's balance) and no Edit control at all; forms are plain `<form>` + `useActionState`, with no form library. `npm run test:mutations` is the integration harness — it rebuilds the local database, signs in as the real owner, and drives the real Server Actions, mutation DAL, and production read DAL, mocking only `lib/data/supabase.ts` plus `next/cache`/`next/navigation` (notably **not** `getToday()`, so the posted-date ceiling under test is the real one). All ten parity-covered `lib/data/**` read functions (`getAccounts`, `getCategories`, `getTransactions`, `getRecentTransactions`, `getBudgets`, `getBills`, `getUpcomingBills`, `getGoals`, `getNetWorthHistory`, `getToday`) are Supabase-backed; CP4's `getMovements(ids)` is the eleventh read function and has no fixture oracle — `lib/mock/dal.ts` never exposed movements, so `npm run test:parity` does not cover it and `tests/mutations/movements.test.ts` proves it against real rows instead. `lib/data/supabase.ts` is the one DAL seam allowed to import `lib/supabase/**`; every read calls `getOwnerId()` (verified via `getClaims()`, never `getSession()`) before issuing its query, independent of route-layer render order. `getAccounts()`/`getGoals()` read the `account_balances`/`goal_balances` `security_invoker` views; `getBills()` is a two-query projection (active `bills`, then their `scheduled` `bill_occurrences`, reduced to one occurrence per bill in TypeScript — PostgREST can't truncate per-parent-row); `getTransactions()` orders `date DESC, created_at DESC, id ASC` and is read through a bounded, cumulative "Load more" reveal window (`app/(app)/transactions/page.tsx`, `lib/data/filters.ts`) — never an unbounded full-history fetch; `getNetWorthHistory()` queries `ORDER BY month DESC LIMIT n` and reverses in TypeScript for chronological display; `getToday()` derives the calendar date from `profiles.timezone` via the real clock (`lib/data/clock.ts`), with no dev-only `MOCK_TODAY` branch — seeded data ages naturally against the real date. `public.movements` was unreadable by `authenticated` through Phase 6 (no grant, no policy) — no Phase 6 read needed it; CP4 added `SELECT` plus `movements_select_own` because the movement **edit** surface is the first thing that has to read the pair as one object. `lib/mock/dal.ts` is retained only as the `npm run test:parity` oracle; no production code imports it. `Transaction.kind` may now be `adjustment`, and `lib/finance/transactions.ts` counts it as neither spending nor income — like a movement leg, it moves a balance without being an economic event. `merchant` search is a plain `ILIKE` scan with no `pg_trgm` index — recorded as a future performance optimization, not a Phase 6 correctness blocker, since it's provably correct against the single-owner dataset. `lib/supabase/**` (browser/server/proxy Supabase clients), `lib/auth/**` (the app-facing identity facade and `signIn`/`signOut` Server Actions), `proxy.ts` (session-cookie refresh via `getClaims()`), `app/(auth)/login`, and the `requireUser()` guard in `app/(app)/layout.tsx` are implemented and verified both statically (`lib/auth/posture.test.ts`) and at runtime (`npm run auth:verify`, `scripts/verify-auth.ts`). No signup route exists, or ever will. Locally, `npm run auth:reset-local` rebuilds the database around one real, login-capable owner at the same deterministic UUID the fixture seed targets — plain `npm run db:reset` alone is not login-capable; rerun `auth:reset-local` after it if you need to sign in. The Supabase schema, RLS/grants, triggers, views, seed data, and the hardened snapshot-writer (Phase 4) are implemented and verified both locally and hosted (`supabase/migrations/**`, `supabase/tests/database/**`) — unchanged since Phase 4 apart from the additive Phase 7 CP2–CP7 migrations above — no Phase 4 migration file has ever been edited (CP3 does drop and re-create `transactions_sign_by_kind_ck` with a wider predicate, in its own forward migration, preserving every existing branch verbatim). `error.tsx`/`loading.tsx`/`not-found.tsx` boundaries exist, `lib/errors.ts` defines the typed DAL error taxonomy, `TransactionFilters` supports `from`/`to`, and `lib/data/**` has explicit ordering contracts. Phase 2 (data architecture & security design) is complete — see `docs/database-schema.md`, `docs/rls-policies.md`, `docs/auth-design.md`. **As of CP7 every finance domain is writable by its owner** — accounts, categories, transactions, movements, reconciliation, budgets, goals/contributions, and bills/occurrences. `net_worth_snapshots` and `profiles` are the only tables `authenticated` may not write, and both stay that way.

**Recurring bills (CP7) are a parent plus a derived rolling schedule, and the two only ever move together.** `bills` holds column-scoped `INSERT`/`UPDATE` and **no `DELETE`, ever** (soft-delete via `is_archived`; `bill_occurrences_bill_fk` is `NO ACTION DEFERRABLE` rather than `CASCADE`, so a hard delete of a bill with any occurrence would fail at `COMMIT` regardless). `bill_occurrences` holds a three-column `UPDATE (status, transaction_id, paid_on)` and **no `INSERT` and no `DELETE`, ever** — it is the one relation `authenticated` may update without being able to insert, because an occurrence is a system-derived fact rather than something a person types, and PostgreSQL has no predicate-scoped `DELETE` that could tell a `scheduled` row from a `paid` one. `amount_cents` and `due_date` are absent from every grant: they are what *that* instance was due for and when, fixed at generation time (`docs/database-schema.md` §13), and neither the owner nor the scheduler may rewrite them. Three `SECURITY INVOKER` RPCs — `public.create_bill`, `public.replace_bill`, `public.set_bill_archived` — exist because a created bill with no occurrence has no projected due date and is omitted by `getBills()` (indistinguishable from a failed create), and because a terms edit must rebuild the future schedule in the *same transaction* as the `UPDATE`, so a refused regeneration rolls the edit back and the old bill and its old schedule survive byte for byte. Only `amount_cents`/`frequency`/`anchor_date` trigger a rebuild; a name/category/account edit rebuilds nothing. **`public.maintain_bill_schedule(p_bill_id, p_rebuild_future)` is the second `SECURITY DEFINER` function in this application** (after CP5's snapshot bridge) and is built to the same rules: owned by `finance_snapshot_writer`, `search_path = ''`, owner read from the request's own JWT claim via `private.request_owner_id()`, and **no owner, month, date range or horizon parameter** — `090-privileges.sql` asserts its argument list is exactly `(uuid, boolean)`. Its one new privilege is `DELETE` on `bill_occurrences` behind the narrowest policy in the schema, `status = 'scheduled' AND user_id = private.request_owner_id()`, so paid/skipped history is unreachable at the *policy* layer before Phase 4's `guard_bill_occurrence_delete()` is consulted, and a claimless session (psql, cron) deletes nothing; it has no `UPDATE` on the table and never will. `authenticated` gains no `USAGE` on `private` and no `EXECUTE` on any generator. **The rolling horizon is one year from the owner's own calendar day**, widened to the bill's anchor when that anchor is further out (otherwise a bill deliberately anchored years ahead would generate nothing and vanish from `/bills`) — a constant in the bridge, unreachable by any client. Generation is **mutation-time maintenance, never a render-time side effect**: no read path calls the scheduler, and opening `/bills` writes nothing. `private.generate_bill_occurrences_for_bill` reuses Phase 4's `private.next_bill_occurrence_date` rather than re-implementing month-end clamping or leap-year recovery; it walks **one bill** and starts **at the anchor** rather than at `max(due_date)`, because `next_bill_occurrence_date` advances in whole periods from the anchor's own month and a due date from the old series can otherwise skip the first occurrence of a new one. It starts at the anchor **only when the bill has no occurrence at all** — true exactly once, at creation, which is what lets someone track a bill whose first due date has already passed; every later call starts at the owner's today, so no rebuild manufactures a past-dated obligation and already-overdue `scheduled` rows are preserved alongside every paid and skipped one. Two guard triggers: `assert_bill_refs()` (`BEFORE INSERT OR UPDATE` — an active category and an active account when either is named (a bill's category **kind** is deliberately unconstrained — no approved pre-CP7 requirement makes it an expense category, unlike CP6's budgets), each half checked **only when its own column changes**, so a bill whose category was archived later can still be renamed, repriced and unarchived) and `guard_bill_occurrence_transition()` (`BEFORE UPDATE` — the state machine `scheduled → paid`, `scheduled → skipped` and either back to `scheduled`; a direct `paid ↔ skipped` conversion is refused and a same-status update is an idempotent no-op; the `paid_on` ceiling is the owner's own calendar day from `profiles.timezone`, never server UTC; and `id`/`user_id`/`bill_id`/`due_date`/`amount_cents`/`created_at` may not move, for **every** role rather than only the one the grant constrains). **Bill tracking creates no ledger activity of any kind** — no CP7 action writes a transaction, movement, account or budget, and none refreshes the net-worth snapshot, because there is no figure for it to recompute; `tests/mutations/bill-occurrences.test.ts` reads every balance, total, cash-flow figure, net worth and snapshot back before and after each operation. Marking paid may optionally *reference* one of the owner's existing transactions, which alters nothing about it (the amounts are free to differ — a bill is an expected obligation, a transaction is what happened); `bill_occurrences_transaction_fk` then blocks deleting that transaction until the occurrence is unmarked, and both `deleteTransaction` (CP3) and `deleteMovement` (widened in CP7, since a movement delete cascades both legs) preflight it and say "Unmark that bill as paid first." Bill and occurrence writes revalidate exactly `/bills` and `/dashboard`. Read side: `getBills()` is **unchanged** and still projects active bills onto their earliest `scheduled` occurrence for `/dashboard`; CP7 adds `getBillsForManagement()` (two queries, never N+1) returning every owned bill with recurrence terms, archive state, full occurrence history ordered `due_date DESC, created_at DESC, id ASC`, and a derived optional `nextDueDate` — optional because a bill whose occurrences are all paid or skipped has no honest due date, which is exactly the case a management view must still show. The `BillOccurrence` DTO carries each occurrence's **own** amount, never the parent's. `/bills` is the management surface (Add bill; per-card Edit, Mark paid, Skip, History, Archive/Unarchive; a separate Archived section that keeps history visible and replaces Edit/Mark paid/Skip with a sentence); the mark-paid form defaults to and caps at the owner's own today, offers a **bounded** deterministically-ordered picker of recent transactions, and says plainly that marking a bill paid does not record spending; history shows Unmark paid / Unskip and **no Delete control**, because no action exists behind one. `billStatus()` is unchanged and remains the authority for overdue/due-soon/upcoming.

- `npm run build` — production build
- `npm run start` — run the production build
- `npm run lint` — run ESLint
- `npm run typecheck` — `tsc --noEmit`
- `npm test` — run Vitest once, fully offline (fixtures + mocked `lib/data/supabase.ts`); `npm run test:watch` for watch mode. Scoped to `lib/**/*.test.ts` (`lib/finance/**` and fixture coherence, `lib/auth/**` unit + static posture tests, `lib/data/**` unit tests) — no component tests.
- `npm run test:parity` — the Phase 6 parity suite (`tests/parity/**`) proving each Supabase-backed `lib/data/**` function agrees with the `lib/mock/dal.ts` fixture oracle. Requires local Supabase running and `npm run auth:reset-local` already applied — not offline like `npm test`. It reads only, so run it **before** `test:mutations`: the mutation suite leaves rows the oracle knows nothing about.
- `npm run test:mutations` — the Phase 7 CP2–CP5 mutation suite (`tests/mutations/**`). Real writes, as a real authenticated owner, against local Supabase: real Server Actions → real validation → real `lib/data/mutations/**` (and, for movements and reconciliation, the real `create_movement`/`replace_movement`/`reconcile_account`/`refresh_current_net_worth_snapshot` RPCs) → read back through the production read DAL. Test *files* are not ordered deterministically by Vitest, so each file's assertions are written to be independent of what the others left behind. Only `lib/data/supabase.ts`, `next/cache`, and `next/navigation` are mocked — `getToday()` is deliberately real, so the owner-timezone posted-date ceiling is exercised rather than stubbed. **Its global setup rebuilds the local database** (it runs `scripts/provision-owner.ts`) and refuses to start unless `NEXT_PUBLIC_SUPABASE_URL` is a loopback address — it can never touch hosted. Runs serially. Rerun `auth:reset-local` afterward to clear the rows it created.
- `npm run auth:reset-local` — rebuild the local database around one real, login-capable owner (`scripts/provision-owner.ts`). Plain `npm run db:reset` alone is not login-capable.
- `npm run auth:verify` — runtime-verify the auth flow against a running `npm run dev` (`scripts/verify-auth.ts`).
- `npm run db:test` — run the pgTAP database test suite (`supabase test db`). It runs against the local database **as it currently stands**: it neither re-applies migrations nor re-seeds (verified directly — a hand-edited row survives the run and fails `010-seed-parity.sql`). So run `npm run db:reset` (or `auth:reset-local`) first whenever migrations changed or the data has drifted, or the suite will report on a stale schema.

## Architecture invariants

- **Money is integer cents**, branded `Cents` (`lib/types`). Never floats, never `parseFloat`. Convert to decimal only in `lib/format/currency.ts`. A `bigint` crossing the DB→TS boundary must pass a `Number.isSafeInteger` check — never silently coerced.
- **Percentages are display-only, divide-first**: `percentage(num, den)` in `lib/finance/money.ts` computes `(num/den)*10000` rounded, never `(num*10000)/den` — the latter can silently exceed the safe-integer range before dividing. Returns `null` for a zero denominator or non-finite result; render as `—`, never `NaN`/`Infinity`. A meter's *text* percentage may exceed 100 (over-budget, over-funded goal) — only its CSS width is clamped to [0, 100].
- **Dates are `'YYYY-MM-DD'` strings.** Never `new Date('YYYY-MM-DD')` on a financial date. Parse via `lib/finance/dates.ts` (`parseCalendarDate`, re-exported from `lib/format/date.ts`); day-count math (`daysBetween`) uses `Date.UTC`, not local-midnight subtraction, so it's DST-safe.
- **Transaction meaning is `kind` + sign together, never sign alone.** `income` +, `expense` −, `refund` +, `transfer`/`credit_card_payment` source − / destination +, `adjustment` either sign. The two movement kinds are paired legs sharing one `movementId` (exactly two, summing to zero), excluded from income/spending/cash-flow but still visible in each account's own history; `adjustment` is likewise excluded (it reconciles a balance rather than recording an economic event) and carries no category. **Entry forms collect a non-negative magnitude and the server derives the sign from the kind** (`signedAmountFor` in `lib/types/enums.ts`, mirroring `transactions_sign_by_kind_ck`) — a signed field would let a well-formed submission contradict its own kind. Zero is legal for ordinary rows and stays exactly `0`, never `-0`. See `lib/types/index.ts` and `lib/finance/transactions.ts`.
- **Account balances are signed** (assets +, liabilities −). Display splits it: `totalAssets`/`totalLiabilities` (positive magnitude) and `netWorth` (signed sum), such that `netWorth === totalAssets - totalLiabilities`. `NetWorthSnapshot` commits to the same convention explicitly (`netWorthCents` stored, not implied) — never compare it against raw signed balances.
- **`today` is always an explicit parameter**, supplied by `lib/data/clock.ts` (`getToday()`, fixed at `MOCK_TODAY` during the mock phase). `lib/finance/**` never reads the clock — ESLint blocks `Date.now()`/`new Date()` there.
- **Every list-returning `lib/data/**` function has an explicit `ORDER BY`-equivalent sort** — see `docs/database-schema.md §17` for the full contract per function. Never rely on fixture array order. When a DAL function only guarantees a *technical* order (e.g. `getBudgets()`'s `category_id ASC`, since it has no join to `categories`), the calling page applies its own semantic display order using data it already fetched — a UUID must never become a visible sort order. `getTransactions()` orders `date DESC, created_at DESC, id ASC`; `created_at` never appears on the `Transaction` DTO.
- **Layer boundaries** (enforced by `eslint.config.mjs` where the layer exists):
  - `lib/data/**` — the only layer that queries the database (or reads mock fixtures now). `'server-only'`, returns DTOs.
  - `lib/mock/**` — fixtures. Only `lib/data/**` may import them; `app/**` and `components/**` are blocked.
  - `lib/supabase/**` — the only layer that reads Supabase env vars / constructs clients. Reachable only from `lib/auth/**` and the root `proxy.ts`; `app/**` and `components/**` are blocked from importing it directly.
  - `lib/auth/**` — the app-facing identity seam: `getVerifiedClaims()`/`requireUser()` (`lib/auth/session.ts`) and the `signIn`/`signOut` Server Actions (`lib/auth/actions.ts`). `app/**` and `components/**` call into this, never into `lib/supabase/**` directly. No `signUp` — public signup is disabled, permanently.
  - `lib/finance/**` — pure calculations: no `lib/data`, `lib/mock`, `lib/supabase`, React, or clock access.
  - `components/**` — UI + local state/interactivity only. No DB/DAL/fixture access, no `process.env`, no derived financial arithmetic (call the tested `lib/finance` function instead), no `lib/supabase/**` or `lib/auth/**` value imports (the action/session helpers arrive as props; a type-only `lib/auth/types` import is fine, since it carries no runtime access).
- **Auth:** use verified claims/user identity (`getClaims()` for page/proxy protection, `getUser()` when an up-to-date Auth record is specifically needed) for server-side authorization — never `getSession()`, since cookie-backed session data isn't itself verified. See `docs/auth-design.md`. RLS is enabled on every table even though this is single-user — the publishable key is public. `service_role` never runs in application code. This posture (no `getSession()` authorization, no `signUp()`, the import boundaries above) is a static regression test, not just documented convention — see `lib/auth/posture.test.ts`.
- **Server Actions are independently reachable endpoints** — re-verify auth and row ownership inside the DAL, not just at the page level.
